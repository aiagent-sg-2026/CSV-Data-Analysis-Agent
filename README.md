# CSV Data Analysis Agent

This repository contains a browser-only React CSV analysis app. It has an editable source package and a checked-in static deployment. No Node.js server is needed when users run the deployed app; Node.js is used to build and test the source.

## Assistant and structural review

Assistant starts expanded on desktop (768 px and wider), while mobile starts with the full-screen drawer closed. You can still hide, reopen, and resize Assistant manually. Resizing preserves its 320 px readable minimum; constrained desktop layouts let the main area shrink below its preferred 600 px rather than collapsing Assistant. Closing and immediately reopening a structural semantic review must not let an older preparation cancel the current review. Semantic confirmation is not Dataset Commit approval: independent validation and separate exact approval remain required. A completed source scan is not proof that repair or model execution succeeded.

## Large-source repair checkpoint (source only)

An opt-in `code.run` mode `source_records` now executes original Blob-backed CSV records in host-owned contiguous batches through the existing QuickJS worker. Request `sourceRecords: {sourceId, sha256, width, initialState}`, `inputs: []`, JSON output and no table/byte-range bindings. The program returns `{state, rows: [{sourceRow, cells}]}`; only lossless trailing-empty padding/removal is currently supported. Every persisted cell is independently rechecked against the full original source, including multiline/UTF-8 tails. Session-scoped OPFS stores immutable ordinal chunks and a hash-chained, sealed manifest, with serial backpressure and quotas; the host does not accumulate all rows or lineage sets. A bounded private digest index (at most 10,000 SHA-256 strings) authenticates random-access chunks without replaying the full spill. Default APIs and their limits are unchanged.

Normal qualified initial Pi analysis now selects bounded record execution from retained-source capabilities and existing budgets rather than rejecting eligible sources above 64 KiB/2,000 records. Small synchronous byte bindings remain compatible; small Blob-only originals can also stream. Pi inspects bounded diagnostics/source ranges, proposes structured meaning through public `candidate_infer_meaning`, authors revisioned JavaScript, executes QuickJS, stages and independently validates a draft, with bounded automatic retry. The structural manifest itself still says `semanticValidation: not_performed` and `commitAllowed: false`: only separate host receipts authorize Draft/exact review. No cap raises, full-array fallback or legacy capacity fallback. The private source/target task ledger retains provider/tool/time/execution usage across goal changes, cancellation and semantic suspension in the same session; saved references are not runtime grants.

Execution and independent validation use separate host-owned sequential parser cursors (64 KiB read-ahead/raw-record/wire-batch caps, ≤50 records and the existing 128 KiB coordinate-object consumer envelope), retaining partial quote/UTF-8/CRLF positions and unacknowledged batches across permitted cancellation. Positional tools keep their independent sparse seeks. Intake hashes once; normal scan + execution + validation reads approximately 3× original bytes (intake's 3-byte BOM probe is counted). The cumulative 600 MiB source-I/O quota reserves requested native read bytes **before** I/O, including failed/cancelled reads; it is not a returned-JSON counter or an OS disk-cache measurement. Batch attempts/steps are charged before asynchronous source work; three cancelled no-progress attempts cannot be reset by resuming. Initial state/dialect limits are checked before scratch allocation, and initialization failures retire only the owned scratch generation; cleanup I/O failure can still leave non-authoritative scratch for session-age cleanup. ## Agent flow

`frontend/index.tsx` boots the React shell in `frontend/App.tsx`. The shell reads state from `frontend/store/useAppStore.ts`, which composes focused state slices. CSV intake enters `frontend/services/agent/orchestration/fileOrchestrator.ts`; planning and analysis run through the agent orchestration/runtime modules, with tool contracts under `frontend/services/agent/tools/` and execution under `frontend/services/agent/execution/`. The app records progress and verification in UI state and browser persistence. The main assistant and governed initial analysis use the browser Pi Harness. The shared demo gateway rejects the Responses API `max_output_tokens` field: Default-provider requests omit it at the final fetch boundary, including Pi and AI SDK calls. The Default provider no longer ships a gateway key: `frontend/services/ai/demoGatewaySession.ts` opens a short-lived `dmo_*` session (`POST /demo/session`, project id from `VITE_DEFAULT_GATEWAY_PROJECT_ID`), and the same boundary injects the bearer token, substitutes the session's model alias, and refreshes once on 401 or the session request cap. PWA updates are automatic by default: `frontend/services/pwa/pwaManager.ts` registers the worker with `updateViaCache: 'none'`, re-checks every 30 minutes and when the tab becomes visible, and applies a waiting worker as soon as the app is idle (`frontend/hooks/usePwaAutoUpdate.ts`; an import, analysis or report in flight defers it, and the existing banner keeps the manual refresh action). The header button (`frontend/components/PwaUpdateButton.tsx`) shows the build version and lets users run a manual check. The importing screen (`frontend/components/ImportProgressCard.tsx`) shows a four-step stage tracker (Upload, Parse, Analyse, Ready) derived from real app state, an indeterminate progress bar, two privacy cards, and an on-demand technical details panel; that general tracker remains indeterminate because the overall pipeline does not report a percentage or ETA. Its separate full-source structural scan panel reports actual bytes and logical records, with cancellation/resume. The Pi follow-up agent supports skills: `frontend/services/agent/skills/builtin/<name>/SKILL.md` documents (pi harness format: `name` and `description` frontmatter plus instructions; metric choice, data-quality check, `data_query` patterns, pivot, period comparison, safe cleaning) are listed in its system prompt by name and description and loaded on demand with the `read_skill` tool; people can add their own skill files in Settings (Agent skills: import `.md` files, remove them; stored in this browser's localStorage, so "Clear all local data" removes them); precedence is built-in, then Settings skills, then workspace files `skills/<name>/SKILL.md` or `skills/<name>.md`, and a skill with the same name replaces the one below it. Its tools include the read-only diagnostics `data_missing`, `data_outliers` and `data_value_counts` next to `data_query`, `data_describe` and the workspace readers. During the initial analysis, Pi first drafts a research plan (`frontend/services/agent/runtime/pi/piResearchPlanner.ts`): it uses the read-only data tools and the metric skill, submits 2-6 structured questions, and the app validates them against the real columns (`researchPlan.ts`) before the evidence stage runs them; if planning fails, the previous topic planner runs. The evidence query planner also receives the text of the metric and query skills plus the person's own Settings skills, and Pi can create pivot, period-comparison, cohort, driver-breakdown and correlation cards in a card request. The checkpoint keeps Pi's research plan so a resumed run continues with it. While the initial analysis runs, the status card shows the working dataset's real row count and a "Stop analysis" button that cancels the run and keeps the last stable dataset. In the initial analysis Pi may skip the optional cleaning stages when the facts show clean data (the host refuses to skip required stages), and when a Pi research plan drove the run, Pi also designs each evidence query with the read-only data tools and skills (`frontend/services/agent/runtime/pi/piEvidencePlanner.ts`), validated by the same SQL evidence validator; if that fails the previous planner runs. Pi also judges which numeric columns can be summed (`ColumnProfile.additivity`, validated by the app; percentage columns are never summable) and that judgement, not column-name keywords, drives the aggregation rules when present. In Settings every skill can be switched off, edited (saving a built-in skill keeps your version until you restore the default) and exported. Direct OpenAI requests keep their normal model settings. The optional Pi Browser Lab remains a separate read-only tool loop over the active React dataset.

The upload screen keeps "Select a file" and drag and drop as the primary action. Below it, a demo dataset gallery (`frontend/components/DemoDatasetGallery.tsx`) lists Singapore open datasets from `demo-data/catalog.json` (schema version 1, fetched with a relative URL so sub-path deployments work). `frontend/services/data/demoDatasetCatalog.ts` validates the catalog: it drops malformed entries, accepts only bare `.csv` file names inside `demo-data/` and `https` source links, falls back to English for missing translations, and falls back to the two built-in HDB datasets when the catalog is missing or has no valid entry. Each card's "Analyse this data" button fetches the CSV and hands it to the normal upload pipeline. The catalog's `suggestedQuestion` is parsed but not passed on, because the upload pipeline takes only a File and resets the analysis goal. The gallery shows 3 cards on phones and tablets and 6 on desktop, with a "Show all" toggle for the rest. The service worker caches the catalog per build version, like other same-origin files.

When the user explicitly asks the main assistant to create a dashboard card, Pi can call the governed `analysis.create_plan` action. The turn succeeds only after the new card exists in app state; the dashboard switches to Explore so the card is visible, and chat links to it. Other follow-up requests use bounded diagnostic/query tools and can propose supported deterministic data mutations through the app's approval flow. A query table in chat alone does not count as a created card.

The browser integration uses `pi-agent-core` and `pi-ai`; it does not embed the complete `pi-coding-agent` CLI execution environment. Follow-up chat exposes selected data queries/diagnostics and workspace readers, on-demand skills, conditional card creation, and deterministic mutation proposals that pass through app approval. Ordinary turns allow three app-tool calls; batch analysis allows eight. The follow-up coding path can write/revise JavaScript and execute it through governed QuickJS workers, with complete memory-table and explicit stateful inputs. If the companion query fails, the card says "Top N of the groups returned" and shows no overall total or percentage. Non-additive measures (average, median, min, max, series that cannot be added) get no share and no companion query. Executive KPIs, aggregation-quality commentary, the report harnesses and the AI summary context use the same true total. The series guard and the evidence value gate read the executed WHERE, that is `query.where` merged with the plan's `preFilter`, so a `RowClass = fact` filter in `preFilter` counts as a detail-row filter.

Messy report-style CSVs (ERP exports, accounting reports, European exports) go through the same intake as clean files. Synthetic fixtures with ground truth for seven layouts live in `frontend/tests/fixtures/weird-reports/` (README, `truth.json`, seeded generator). Dialect detection follows RFC 4180: line breaks inside quoted fields are valid, a BOM is stripped, a `;`, tab or `|` parse that splits every record beats a `,` parse caused by decimal commas, and trailing empty columns are dropped. Numbers are read per column: a column that has an unambiguous decimal-comma cell and no US-style cell is a decimal-comma column (and never an identifier column by header name), `1,234` stays US thousands otherwise, and Swiss `1'234.50` and Indian `12,34,567.89` agree across the profiler, DuckDB, Arquero and the JS executors. A space-aligned text report saved as `.csv` is detected as not delimited and, when the column gaps are consistent, split by position. Header detection skips a long key-value preamble (up to 200 rows), folds grouped two-row headers into `FY2025 :: Q1`-style names, and takes an all-caps label row directly above the records as the header. Several different tables stacked in one file are not merged: the first table is analysed and the others are set aside and named in the review dialog. Inside the body, page breaks (with repeated title and header rows), blank spacer rows, and sub-total or total rows are classified and kept out of the detail table. A sub-total is removed only when its amount reconciles with the rows it sums, so a business named "Total Solutions" stays. A page-marker row is removed only when the whole cell is the marker and it recurs next to a repeated header. Indented labels become `ParentSeries`, `HierarchyDepth` and `RowClass` (`fact` or `subtotal`) when the parents equal the sum of their children, and carry-forward columns (a customer printed once per group) are filled down, including on melted tables. The structure review dialog is only shown when something still needs a person. After a person confirms it, analysis starts: a failed cleaning run that was only the post-import marker (`CleaningRun.failureOrigin = 'initial_analysis'`) no longer takes precedence over the confirmed structure, while a real cleaning failure keeps its text and still blocks. A header layer counts as retained (`label_layer_retention_complete`) when every band label is part of a column name. Every blocked state states its reason in plain language with a next action, and internal check codes appear only under Technical details.

Round 7 additions to the same area. After a CSV loads, `numericParseGuard.ts` re-reads every numeric column from the original text and compares it with the loaded values; a mismatch (for example a decimal-comma column read as thousands) raises `numeric_parse_mismatch` and no card from that column can be Verified. Cleaning that goes through the AI plan or a `cast_column` operation uses the same per-column number style, so a European measure is no longer stripped of its commas. For hierarchy tables every planner, gate and card path reads detail (`fact`) rows only (`rowHierarchyGuard.ts`); parent rows can no longer be double counted, and a model-written cleaning step cannot touch them. The investigation harness no longer treats two labels whose totals are within 1% as aliases unless the labels also look alike (`areLikelyAliasLabels`), and when the detail-row contract is verified it injects no `NOT IN` label exclusion list: on the synthetic hierarchy report this removed a silent 3% undercount (Overall now 44,403,225, EUROPE 12,092,419). A ranking that is cut off reports the true group count, true total and an "Others" share; for a non-additive measure it says "Only the groups returned". Identifier columns are kept out of ranking dimensions, and the money measure leads when several measures exist. Labels, plurals, titles and import notes go through shared helpers (`displayText.ts`, `bandLabels.ts`, `setAsideTables.ts`) so results read as finished copy.

Wide tables whose headers are periods (`DataSeries,2025,2024,...` or `2026Aug,2026Jul,...`, as SingStat publishes) are melted at intake by `frontend/services/agent/reportShapePeriodWide.ts` into `DataSeries`, `ParentSeries`, `HierarchyDepth`, `RowClass` (fact/subtotal/total), `Period` (ISO date), `Value` and lineage columns, through the existing unpivot and structure-verification path. A repeated child label gets a unique key such as `Citizens > Male`. Intake also decides whether the series can be added together. Series count as additive unless the published numbers contradict it: a parent that does not equal the sum of its children, or an indented table with several unrelated roots. When they are not additive (the public-transport demo mixes km and daily ridership), `services/agent/planning/seriesMeasureGuard.ts` rejects or replans any analysis that aggregates `Value` across series. It keeps per-series comparisons table-only and drops the total KPI. Topic planning, Pi research, and chat and skill cards all go through the same check. The Default demo gateway rejects structured-output schemas with objects nested deeper than 4 levels, so the evidence-plan output schema carries per-aggregate filters as a flat `aggregateFilters` list that is lifted back into the plan before validation.

Metric choice is checked against data, not column names. The Pi research planner must classify every summed metric (additivity, plus a nature that now includes `identifier`). A grouped SUM whose group ranking follows the group row counts (Spearman ≥ 0.9 over at least 4 groups) is sent back for a median/average unless the plan sets `total_intent`. At card level the same check marks such cards `volume_driven_sum` (caveated) or `volume_driven_total` (note only). Time dimensions are exempt. In the qualified cleaning window, rejected `candidate_infer_meaning` proposals no longer close the cleaning skip; only accepted meaning, executed code, a staged candidate or a successful workspace write do. The `applyTransform` gate names the exact skip call. Repeated rejected proposals get skip guidance, or end the run as blocked with `initial_cleaning_meaning_no_progress` instead of exhausting the 240 s budget. Pi `workspace.*` tool results include the listing or search output. `streamGenerateText` surfaces provider HTTP errors so status-based retry works; 400/413 and demo-gateway quota or limit errors are never retried. `data.query` accepts `select: ['*']`.

A ranked card keeps the direction of its evidence query. When the query orders its measure ascending (for example "lowest pay first"), the card plan records `rankDirection: 'asc'`. The chart, table, top-N window, export scope and executive KPI then keep the lowest groups first and say "Lowest N" instead of "Top N". Groups with no value (a NULL median) go last in either direction. A grouped non-count evidence query also runs a read-only COUNT companion over the same population (`frontend/services/agent/planning/groupSampleSize.ts`). If one of the three leading groups has fewer rows than `max(5, min(30, 10% of the median group size))`, the value gate adds `small_group_leader` and a `sampleSizeCaveat`. The card shows "X (rank 1) is based on only N rows", and the evaluator marks it `small_sample_leader` (caveated), so it cannot lead the trusted headline. When the typical group itself has fewer than 5 rows, the comparison is at row grain and is not flagged. A top-N window whose shown values are all identical shows a "Tied values" note and is marked `tied_leading_values` (caveated). The presentation decision does not change in either case.

### Supported spill-backed exact commit (2026-10-27, source-only)

The opt-in host-declared ordered-source-record candidate now connects independent validation → suspended read-only draft → existing **Review / Approve** → immutable local accepted CSV → isolated DuckDB activation. Approval binds the exact source/dialect, session/task/program, meaning/units, receipt and spill generation. Draft reads and saved metadata never grant commit; stale, denied and repeated approvals cannot publish another version. Failed copying/loading/persistence preserves the previous accepted data; failed publication has journal CAS compensation and worker rollback.

Accepted rows are retained automatically outside temporary session storage. After reload, use **Restore local rows** (full bounded backing-integrity verification), or **Reattach original CSV** (also verifies the original source). An interrupted unapproved proposal requires explicit source revalidation, a new execution/receipt and fresh exact approval. Missing/corrupt storage blocks queries rather than falling back to preview rows. **Clear all local data** removes this backing too. Optional seven-day row-retention and append-rollback controls remain legacy small-lane features, not qualified spill operations.

Supported meaning is one table, original first-row header, one-to-one column mapping, source-record grain, identity/trim and strict decimal scale 0–6 with host-resolved units; optional last-record numeric summary is reconciled exactly. This does not prove business meaning, natural-key uniqueness or unit homogeneity. DECIMAL storage, scalar/membership/range filters and SUM preserve base-10 values (filter literals must be plain decimals with at most six fractional digits). Multi-period SUM/MIN/MAX and COUNT DISTINCT now share typed decimal row totals: compatible scales are added exactly, partial NULL periods add nothing, and all-NULL rows remain missing. Native decimal overflow fails rather than approximating. Mixing validated exact decimals with unproven non-decimal columns fails explicitly (`exact_decimal_period_mixed_types_unsupported`); missing/different resolved units require meaning clarification (`exact_decimal_period_units_require_meaning`), not guessed conversion. Presence-only COUNT needs no addition or unit conversion. Ordinary nonexact CSV coercion is unchanged. AVG and other floating statistical operations are not exact-decimal arithmetic guarantees. Bounds include 100 MiB original/200 MiB retained source handles per session, 256 KiB scratch chunks/10,000 chunks/256 MiB per generation, 256 MiB accepted CSV and 256 KiB accepted manifest, plus existing cumulative execution/read/step/task budgets. These are ceilings, not a 100 MiB qualification; automatic retention has no new global generation-count quota and remains subject to browser storage quota.

Qualification uses synthetic >25 MiB Files, real QuickJS/OPFS/React approval/DuckDB/IndexedDB and ten fixed-oracle queries, not live AI or arbitrary business datasets. General large-source coordinator/model meaning compilation, compressed/dual-grain ERP and full-product/100 MiB qualification remain open. The checked-in root deployment is unchanged; this package is active only in a newly built `frontend/dist`, not the old root bundle.
