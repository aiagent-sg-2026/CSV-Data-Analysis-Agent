# Bounded dual-grain exact commit and restore

The small complete-envelope lane supports independently validated drafts, separate exact human all-table approval, isolated native DuckDB activation and explicit durable reload recovery. This is not streamed multi-table or live-model qualification.

## Production path

`runPiInitialAnalysis` retains its original-source repair phase and ordinary-analysis lock. A verified retained small source can reach normal Pi structured proposals even when the header solver found semantic alternatives; solver scores are never semantic confirmation. Unavailable/unverified sources keep the existing fail-closed review.

1. The provider inspects original scan/record evidence using existing positional tools.
2. `candidate_infer_meaning` receives `{input,interpretations:[{label,meaning},{label,meaning}],assumptions}`. Each meaning is a complete `DualGrainCandidateMeaning`, not candidate rows or a self-test verdict. Both mappings must pass host structural/source accounting checks before clarification.
3. Existing semantic clarification displays A/B/Neither with exact full mappings and source SHA. The live private capsule binds source custody, source metadata, dataset/input lineage, task revision/scope/goal and the displayed question/options. Persisted IDs, altered labels, free text and model confirmation flags grant nothing.
4. A/B records only the selected complete interpretation. The resumed normal Pi submits the exact chosen proposal; host recompiles its per-table schemas, row coordinates, conversions, grains, keys, units, relationship and exclusions before code execution. Selection identity participates in the host contract digest and is rechecked during the execution/staging/validation lane. Neither stops before a program executes.
5. Provider-authored revisioned JavaScript reads the entire protected original byte range in actual isolated QuickJS and emits the existing closed CandidateOutput v1 envelope with both tables and complete lineage. No trusted host reference rows are fed to the guest.
6. Existing staging authenticates the actual program/input/output receipt. The independent host validator reads original records again, compares every value and cell lineage, verifies unique grain keys, full source-cell accounting, exact decimal groups and many-to-one coverage without fanout. All included additive cells have one owner, including across source aliases. Numeric values are never accepted from a matching total alone.
7. Existing React Task inspection → Review shows both tables. Each **Read draft from start** / **Next draft rows** read is bounded and read-only. Live immutable custody, not the saved UI projection, authorizes a page after the execution lease closes. It checks session, source, original dataset, task/goal/scope/revision and actual program/input/output revisions. A digest mismatch fails closed.

No draft enters accepted CSV/canonical data, accepted DuckDB, answer evidence, cards, memory, exports or reports. Only privately inferred, source-bounded two-table candidates with complete independent receipts and recovery material can request exact approval. Other inferred dual candidates retain `candidate_multi_table_atomic_promotion_unavailable`. Copied, mutated or cross-namespace bindings cannot shed private custody. The primary must be the entity side of the many-to-one relationship.

Exact review binds both schemas/rows, relationship, grain/units, source/hash/version, selected meaning contract, program/revision/inputs, validation, namespace, task/session/goal and target commit/bundle. React displays both row counts and key relationship; meaning selection is never approval. A live exact approval is consumed once. Preparation writes a new authenticated OPFS generation (bounded complete recovery JSON plus manifest, using the existing accepted-storage adapter) and loads both tables in isolated native DuckDB workers before journal CAS. Neither table has a query route before synchronous all-table activation. Persistence/prepare/activation failures roll back workers and compensate the journal, preserving the prior accepted version; uncertain durable outcomes remain fenced.

Queries use structured `plan.tableId` to select exactly one accepted grain; omission selects primary entities. Each worker imports explicit VARCHAR/DECIMAL(24,scale), preserving null versus quoted empty text and zero/negative decimals. Raw SQL, unpivot and joins are unsupported in this lane, avoiding summary/detail fanout. Query identity includes the selected table and accepted version; independently issued evidence must match the same table scope. Existing ordinary/general multi-table/single-table APIs remain unchanged.

Routing custody is host-only and non-serializable: the installed route is bound to the current session/epoch, accepted commit and the entire bundle metadata (all table schemas/storage/versions plus relationship generation). Filename/primary-content equality is not authorization. All managed, raw and specialized query entry points reject known stale owners before execution and after asynchronous results. A legitimate clone requires the live verified binding's explicit host `bind`; copied provider metadata cannot obtain that binding. History deliberately creates a new tab session: verified reconstruction installs fresh custody there while retaining the journal's original accepted-commit identity.

Ordinary, spill and dual transitions prepare workers without retiring prior accepted workers. Activation captures the outgoing route; rollback restores it and finish retires it only after publication. Ordinary replacement of an already accepted generation prepares before journal admission and compensates failed activation. Rollback restores route and publication before awaiting compensation, so unrelated observers cannot retire the prior workers during that wait. Uncertain acknowledgement retains the old physical route/backing while formal evidence remains fenced by `commit_unknown`. Upload/source replacement and New Session revoke custody; in-flight results cannot cross a successful replacement. No additional source-sized hash or row materialization is used for routing.

After reload, **Restore local rows** verifies the already-approved manifest/backing hash, source, program/environment, independent receipt, schema/table counts, keys, relationship and complete lineage before preparing both isolated workers and activating. Drafts and saved approval copies cannot restore authority. Integrity checks are corruption detection, not protection against a same-origin attacker rewriting every trusted journal and checksum.

## Bounded contract

- One complete original source; no table inputs for this mapping.
- At most 65,536 original bytes, 2,000 physical CSV records (not physical text lines), 200,000 source cells and 65,536 bytes of alternatives JSON.
- Exactly two tables, one many-to-one relationship from detail to primary. Primary has one projection. At most 256 columns/projections, 50,000 total output rows, 80,000 output cells and 1,048,576 complete output JSON bytes. Existing guest/workspace/lineage/time/tool limits still apply; no limit is raised.
- Each column has a verbatim source-header coordinate, explicit type/null/conversion, and numeric scale 0–6 plus source `[unit]` annotation. No invented units, currencies or unit conversions. Heterogeneous-unit aggregation is unsupported; preserve non-additive values as strings or stop for a corrected interpretation.
- Projection values come from the current included source record. Only nonnumeric dimensions may instead use an explicit excluded-header `sourceRow`. Strings/dates form unique nonblank grain keys. Keys and relationship origins cannot be synthesized.
- **Wide source records:** both tables use identical record ranges. Detail FK coordinates must match primary key coordinates on that same source record; primary values are not copied into additive metric facts.
- **Document-header/detail source records:** the ranges are disjoint. Each included detail references the immediately preceding included document header, with independently checked source key equality. Cross-group references fail even if a matching key exists elsewhere. Amounts in source document headers and details remain distinct owners at distinct grains; they are not combined into one sum.
- Header rows must be source-referenced nonnumeric headers, or exact repeats of those headers. Numeric/date-leading header cells are unsupported by this deliberately narrow contract. A proposed header role cannot discard numeric detail records. Notes must be entirely blank. Duplicate exclusions require an identical retained record.
- Only explicit grand-total footer alignment is supported: `cells` must cover every real footer column exactly once. Nonnumeric label cells are explicitly excluded; each numeric `sum` cell names a table and metric and checks **all** its rows with exact minor-unit arithmetic. Ragged footer width is preserved, never padded. Subtotals, scoped/mixed-unit summaries, percentage arithmetic and arbitrary footer realignment remain unsupported. Footer role is confirmed by meaning selection; arithmetic equality independently verifies its values, not its role.
- Blank numeric source cells become null only under `decimal_or_null`; zero and negatives remain numeric. Other missing markers/currency stripping/permissive numeric parsing are unsupported. Floating representations that do not round-trip to exact declared minor units are rejected rather than silently rounded.
- Draft pages return at most 10 rows through React (50 at the lower-level API), bounded to 64 KiB including lineage samples. Live-only custody expires five minutes after validation or on source/task/program/session change. Reload does not reconstitute a selection, validation or commit grant. A fresh normal repair/validation must respect the retained source/task budget floors.
- Larger sources remain on existing supported single-table streaming contracts or stop with an explicit unsupported dual-grain size/structure error. There is no automatic dual-grain flattening or full-array fallback.

The browser driver additionally exercises separate React exact approval, ten independently expected table-scoped native DuckDB questions and true reload/Restore local rows, plus denial and unsupported joins. The A42 scenario additionally continues within one session from A to B with identical primary rows but changed detail alignment (reported-value count for Period1:Category1 changes from 0 to 3), rejects the prior dataset/table ID, then uses normal public tools, QuickJS, validation and exact React approval to publish the same primary as an ordinary single-table generation. Native raw SQL returns 3 entities/400 total; explicit existing retention and true reload/restore preserve that result. Focused worker-routing tests also cover host clone rebinding, session/upload/bundle/table revocation, late managed/raw results and rollback. Additive real-QuickJS transaction-model tests preserve a prior dual bundle on ordinary preparation/activation/unknown-ack failures; the original recovery positives remain unchanged. These are deterministic provider tests, not live-model answers or large dual-grain qualification. All external requests are aborted locally before dispatch; any UI `/demo/session` bootstrap attempts are retained in browser evidence rather than described as zero external attempts. `dualGrainCommitCompatibility.test.ts`, the restored HEAD positive multi-table recovery test and an additional positive general multi-table commit test cover the compatibility/security boundary.
